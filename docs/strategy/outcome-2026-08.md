# orghを「アウトカムで」強くする(2026-08-18)

> 問い: 見た目や機能ではなく、**利用者(オーナー1人)に届く実際の成果**を増やすには何を変えるか。
> 方法: 全ミッション履歴の監査 → リーク特定 → 30日運用プロトコル → 証明されたものだけ実装。
> 前提文書: `direction-2026-08.md`(機能の取捨) / `harness-landscape-2026-08.md`(競争環境)。
> 結論を一行で: **作る前に測る。オーナーが入力しない前提で設計する。使う前に「orghでやるべきか」を問う。**

## 1. 定義: usage と outcome は別物(二段階)

- **usage(利用)** = 成果物が参照・デプロイ・公開・展開された**事実**。機械検知できるものがある
  (デプロイログ・公開URL)。ただしusageは**アウトカムの必要条件であって十分条件ではない**
  (「デプロイされたが誰も使わない」はusageありoutcomeなし)
- **outcome(変化)** = オーナーの生活・事業・キャリアの**測れる変化**(期限内に発券できた・
  意思決定が速くなった・売上が生じた)。**起票時に期待変化と観測期限を宣言した案件についてのみ**
  事後判定する(宣言なしに事後で「変化があった」と言うのは外部要因の誤帰属を招く)
- proxyは数えない: テスト数・合格率・ミッション数・起票数・**API費そのもの**は運転指標
- **真の原価はAPI費+オーナー能動時間**。過去分のオーナー時間は再構成不能のため監査(§2)は
  API費のみで行うが、今後の記録(§3)には `owner_min`(オーナーが使った分)を必須で含める

## 3. 30日運用プロトコル(2026-08-19〜09-17) — 実装はこの結果を見てから

**このプロトコルが直接生むのは計測能力と適用判定の初期データであり、アウトカムの増加
そのものではない**(r12指摘を明記)。介入(実装・ルール化)の採否は計測結果が決める——
計器なしの介入は当てずっぽうであり、それが§2の監査が示した現状である。
正本 `docs/ops/outcome-log-2026-08.md` とHANDOFF.mdへの引き継ぎ節は**作成済み**(2026-08-18)。

### 3.0 記録の正本と役割(全実験共通)

- **正本**: `docs/ops/outcome-log-2026-08.md`(git管理・1行1レコードの表。
  書式は §3.0.1。**verdictのreasonには埋め込まない**——reasonはcriteria蒸留LLMと
  escape記録に流れるため、outcome情報の混入は既存処理を汚染する)
- **記録者**: オーナー(裁定のみ)+セッションAI(転記・集計。週次セッション時に
  オーナーへ対象を最大3件だけ口頭確認し、表を更新する。`HANDOFF.md` に本プロトコルの
  引き継ぎを記載し、セッションが替わっても継続する)
- **集計**: スクリプト可読な表書式のため `grep/awk` で機械集計可能。30日後レポートの
  作成者=セッションAI、判定者=オーナー
- **通知疲れ対策**: 週次確認は最大3件・高額順。期限切れ(observe_by超過)は自動で
  `unknown-expired` 確定とし、それ以上追わない。unknown率>50%でそのメトリクスを無効表示

#### 3.0.1 outcome-logの書式(1行1レコード、追記型)

```
| mission | 分類 | usd | route | usage | outcome宣言 | observe_by | 判定 | evidence | owner_min |
route: orgh|manual|ai-session|dropped(適用判定=リーク6の計測。理由を必ず併記)
usage: referenced|deployed|published|delivered|none / 判定: used|unused|unknown|unknown-expired|pending
outcome宣言: 起票時に期待変化を書いた案件のみ事後判定(1行・`|`は使わず／で代替)
observe_by: 種別固定表(配達=+3日/公開物=+14日/UI・アプリ=+30日/業務=+90日)。変更は理由付き追記
outcome_result: achieved|not-achieved|unknown|pending|-(宣言なし)。**outcome宣言のある案件は
  usage判定と独立にoutcome_resultを判定する**(usedでもnot-achievedがありうる。30日・90日レポートは
  usage率とoutcome達成率を別々に報告する)
数値: usd小数2桁・owner_min整数・空欄は`-`。更新は行追加(同mission最新行が有効)
不在耐性: 週次が2週連続で開けない場合 `PAUSED` 行で時計停止(不在をunknown-expiredへ変換しない)
```

### 3.3 即時実装(プロトコルを待たないもの)

**H0① スリープ復帰検知**のみ: executorがwall-clock飛び(>120秒)を検知→実行中workerの生存確認
→**worker死亡かつタスク未コミットの場合のみ**attempt失敗で自動回収。コミット済み・外部副作用の
疑いがある場合は `unknown`→人間確認のまま(**A5の復旧意味論を破らない**)。見積: 2-4h+テスト5本。

**directionの実行順との関係(一本化)**: 本プロトコルが凍結するのは**計測系の新規実装**
(outcome/draft等)のみ。direction文書の実行順——3a'成立条件2件目→3b'(writeback_pending)→
A7 action——は**実害で正当化済みの配達・信頼性投資であり、30日を待たず独立に継続**する。
3b'の開始条件はdirection(3a'成立後)が上位。E1が成功していれば3b'実装時にpending-action共通
基盤と統合設計し、E1が失敗しても3b'自体は実施する(writebackは配達契約でありusage計測と別物)。
全体の実行順の唯一の正はHANDOFF冒頭の実行キュー。

## 4. やらないこと(アウトカム視点で棄却)

- **多人数対応・公開配布**(direction §3.2の再確認)
- **クラウド実行・sandbox等の差別化目的の基盤拡張**(信頼性投資H0①と混同しない)
- **実行中コストのリアルタイム警告**: 計上がadapter呼び出し完了後のため原理的に事後。
  E2の起票時宣言+既存予算停止で代替(「強制」ではなく警告付き運用と正しく呼ぶ)
- **A9実物観察の前倒し**(escape3件ゲートは既決。E5はゲートを迂回しない)
- **verdict reasonへのoutcome埋め込み**(蒸留・escape処理を汚染するため禁止)
- **ダッシュボード**(可視化の磨き込みはアウトカムでない)

## 5. この方針の反証条件

1. **E1記録率<50%**(単独で発火。§3.2と同一条件)→ オーナー入力依存の計測は行動特性に
   合わない。機械検知usageのみの自動台帳へ転換し、**E2/E3/E5の人間入力運用も同時に終了**する
   (E4は独立に判定: メモ0件ならH4永久見送り)
2. **E2運用後も費用超過型の失敗が再発** → 宣言では防げない。呼び出し前の上限強制
   (adapter改修)を再検討
3. **「orghを選ばなかった理由」の上位が構造的**(例: 緊急すぎる・対人调整が要る)→ 次期の
   比較設計でその案件種を重点検証し、優位が出なければ起票しないルール化を検討する
   (orghを強くする=使い所を狭める、も正解に含める)
4. **E1が標本不足で1回延長後(計60日)も閉じない** → orghの利用頻度自体が想定より低い。
   強化投資の前に「そもそも使う場面を増やすべきか/このままでよいか」をオーナーと再設定する
