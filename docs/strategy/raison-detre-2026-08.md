# orghの存在理由(2026-08-21) — Claude Codeがあるのに、なぜorghか

> 問い: Claude Code(以下CC)が高機能化した今、orghは相対的に価値を出せているか。
> 無駄はないか。あり方から再考する。
> 方法: Fable(CC上のAI)とGPT-5.6(Codex)の敵対的弁証法。Fableは「CCの現行機能の生き証人」
> としてCC側の最強議論を提供し、同時にorghの1週間の実運用当事者として実データで答える。
> 各論点は「認めた/反駁した/検証条件付き」で決着を記録する(§5)。

## 1. 前提事実: Claude Codeの現行機能(2026-08、Fableの一次知識)

CCは既に次を持つ: サブエージェント(Agent tool・並列・独立文脈)/Workflow(決定的な
マルチエージェント編成・バックグラウンド実行)/バックグラウンドタスクとMonitor(通知駆動)/
cronスケジュール/スキル(再利用可能な手順書・自動起動)/永続メモリ(セッション横断)/
CLAUDE.md(常時注入指示)/hooks(ツール実行への介入)/MCPクライアント(外部ツール接続)/
git worktree分離/plan mode/マルチエージェントクラウドレビュー(/code-review ultra)/
ヘッドレス実行(claude -p)/セッションresume。

**つまりorghの機能の多くに、CCネイティブの対応物が存在する。**

## 2. 実証データ: この1週間、私(CCセッション)は何をorghに投げ、何を自分でやったか

2026-08-15〜21のセッション実績(この文書の最良の証拠。理屈でなく行動が示した境界):

| セッション直接でやった | orghミッションに投げた |
|---|---|
| 戦略文書の執筆・改稿(Codex 30ラウンド超) | copyback契約の実装(2ミッション) |
| criteria承認・supersede・verdict裁定 | supersede機能の実装 |
| 小さなバグ修正(notify・gitignore・テスト1本) | スリープ復帰検知の実装 |
| マージ・watch再起動・検収 | Notion MCP連携の実装(2タスク) |
| プライバシー事故対応(filter-repo) | 期日ブリーフの生成・配達 |
| 監査・分析・意思決定の補佐 | — |

観察される事実上の分業: **「判断・対話・非定型」はCCセッション、「AC が書ける実装」はorgh**。
そして重要な観察——**orghの現在の実質的な利用者はオーナーではなく、私(CCセッション)である**。
起票・承認・検収・マージの操作主体はほぼ私で、オーナーは裁定(approve/verdict)のみ。
orghは事実上「CCセッションが使う、検収ゲート付き非同期実行サービス」として機能している。

## 3. 立論: orghの非冗長コア(CCで代替できないもの)

Fableとしての正直な仕分け。CCネイティブで**代替できる/できつつある**もの:

- 並列実行・worktree分離 → Agent tool/Workflowで可能
- 教訓の蓄積 → メモリ・CLAUDE.md・スキルで可能(playbooksと機能重複)
- レビュー → サブエージェントレビュー・/code-review ultraで可能
- 定時実行 → cronで可能
- 外部ツール接続 → CCはMCPクライアントそのもの

**現時点でCCが持たない**(=orghの非冗長コア候補):

1. **セッションから独立した常駐実行**: watch/queue/leaseはセッションの生死と無関係に
   ミッションを完遂する。CCのバックグラウンドタスクはセッション文脈に紐づく
2. **承認制の規範台帳と、その強制注入**: criteriaはオーナー承認を経てReviewerの独立文脈へ
   注入される。CLAUDE.mdは「書けば効く」が、承認ゲート・代謝(supersede)・引用統計を持たない
3. **検収の独立性の構造的保証**: Reviewerはworker生成物を読まない設定で起動される
   (買収防止)。CCのサブエージェントレビューは呼び出し側の文脈設計に依存する
4. **監査台帳**: ledger(全イベント・コスト・escape・verdict)は再現性と説明責任の正本。
   CCに相当物はない
5. **オーナーの3接点への圧縮**: 書く(ノート)・承認する・検収する。CCは対話が前提

## 5. 論点別決着記録

### R1(役割: 不要論弁護人/無駄の検察官/あり方の建築家)

**【採択】第6案F「証拠駆動の実行保証器」(建築家提案、Fableが修正のうえ受諾)**
orghの定義: 「ACの実行、証拠の固定、独立検収、失敗時の停止・復旧を保証する単一クライアント向け
実行保証器」。①人間裁定を全件の燃料にしない(機械検証で閉じられる案件は証拠付きで閉じ、
owner verdictは高リスク+無作為抽出に限定) ②watch/queue/leaseはCC側の代替契約が実証される
まで保持(撤去は思想でなくARCH-004の移行試験の結果) ③Dは外部エージェント2種×各3件の実需が
出た時のみ昇格候補。**Fable修正(F')**: Fの定義に「承認制規範台帳」を中核部品として明記する
——検収の質が規範で駆動される点はorghの検収を「ただのAIレビュー」と分ける本質であり、
実行保証の一部である(GPT側もCLAUDE.mdに承認ゲート・代謝・引用統計が無いことは争わなかった)。
最終配置: **F'本線 / B=ARCH-004の撤去手順 / D=実需発生後のオプション / E=12月判定の対照仮説**。

**【反駁】「wrapper4本で再現可能」(不要論§CC代替構成)**
薄いグルーが薄いのは初日だけである。tick.shのflockはleaseの、state.jsonは冪等性・巻き戻しの
再発明であり、orghの実装行数の大半は「wrapper構成が実運用で必ず踏む穴」(スリープ凍結・二重実行・
検収者買収・非git成果物の配達・部分失敗)を先に踏んで塞いだ結果である。信頼性税は実装形態に
かかるのではなく**運用要件(常駐・無人・完遂保証)にかかる**。ただし譲歩: 今日ゼロから作るなら
CCネイティブ+薄いグルーから始めるのが正しい。orghの正当化はサンクコストではなく
「税を払い終えて検証済みの契約群が既に動いている」ことにある。
→ **検証条件**: 比較実験(下記)でwrapper側の隠れ税を実測する。

**【認めた】「3接点への圧縮」は実績でなく設計仮説(不要論§5・検察§4)**
CCセッションへの運用労働の転嫁は事実。実績表現から設計仮説へ格下げし、owner_min計測
(30日プロトコル)で検証する。ただし部分反駁: 転嫁先がAIである限りオーナーの実時間は浮いており、
「転嫁だから無価値」にはならない——測っていないだけ。

**【認めた】検察の個別判決**
GUI $131: 有罪(追加投資凍結は維持。既存分の価値はE1データのverdict裁定UXとして事後判定)。
playbooks自動注入: 有罪+**廃止を前倒し**(「A7前後」→即時。§7)。
Notion: 分計を受諾——orgh製品会計では重複、オーナー人生会計ではキャリア資産(outcome-logの
分類にキャリア枠を追加)。自己監査コスト: 一部同意(計測の計測は今後しない。30日プロトコルの
枠内のみ)。信頼性税$84.83: 部分反駁(sleep復帰等はローカル常駐の税であり、wrapper構成でも
同額発生する)。

**【採択】比較実験(検察・不要論の共通提案をFableが設計統合)**
30日プロトコルのroute記録を拡張し、**同種案件の意図的割り付け**を行う: 次の同規模実装案件を

### R2(役割: 信頼性税の再攻撃/F'整合性検査/実験設計監査)

**【譲歩・境界修正】信頼性税の帰属(R4)**
CCネイティブ(バックグラウンドセッション・Workflow・cron等)は汎用実行配管の税を
**Anthropicが肩代わり**する構造であり、「税は形態非依存」というFableのR1反駁は
汎用配管には当てはまらない。譲歩する: **queue/lease/watch/sleep復帰/worktree編成は
競争優位ではなく「CC移行待ち負債」**(動く資産だが、代替契約成立とともに移管すべきもの)。
GPT側も同意した**移管しても消えない非冗長コア**: ①承認制criteria台帳(supersede・版固定・
引用統計) ②worker/Reviewer分離の検収契約 ③AC→証拠→判定の監査 ④**ローカル非git領域への
manifest付きcopyback(CCクラウドは到達できない)** ⑤copyback_partial/conflict等の停止意味論。
→ 最終判決: **F'縮小版を本線とし、Bを「受動的な撤去手順」から「能動的な税移管計画」へ昇格**。

**【採択】人間裁定の用語3分離(R5)**
F'の「人間裁定を高リスク+無作為抽出に限定」はowner verdict(成果の事後gold判定)のみを指す。
external approval(外部副作用の事前許可)=該当操作で全件必須、criteria approval(規範変更)=
全件必須、E1 usage確認=別契約(週次総量規制済み)。この4区分をF'定義に組み込み、
direction §11・Phase 2設計との衝突を解消。

**【受諾】比較実験の三段階再設計(R6。Fableの交互配分案は棄却が正当)**
自己計測問題(Fableが割り付けと計測を兼ねる)と恣意性の指摘を認める。採択設計:
①**今期(30日)は観察のみ**——全実装案件の開始前属性(規模・種別・AC数)を記録、routeは変えない
②9/17に適格候補6件以上の見込みを判定→見込める場合のみ**次期に3マッチドペアの無作為化パイロット**

③パイロット通過後にのみ**ARCH-004障害試験**(スリープ・中断・再開の固定シナリオ、
CCネイティブ最強構成=第三群を含む)。運営費上限: owner 60分 or 名目20 USD超で停止。
候補6件に60日超なら「比較需要が低い」として判定不能終了。

## 8. 最終結論(9ラウンド+較正で収束)

**問い「orghは相対的に価値を出せているか」への正直な答え: 未判定。
ただし存続を許す暫定根拠はある(利用の実績と、CCが払えない非冗長契約の存在)。
判定は12月の存続条件で下す。**(R4較正: 「限定付きイエス」は証拠水準を超えていた)

- **使われている**のは事実(この1週間で12ミッション、CCセッション自身が主要利用者)。
  だが**価値の因果証明はゼロ**(usage/outcome記録が始まったばかり)
- **実行配管**(queue/lease/watch/worktree)は競争優位ではなく**CC移管待ち負債**。
  Anthropicが信頼性税を肩代わりする構造には勝てないし、勝つ必要もない
- **移管しても残る非冗長コア**: 承認制規範台帳・独立検収契約・監査台帳・ローカル
  private領域へのcopyback・停止意味論。ただし「非冗長」を「価値」と混同しないため、
  §5-R3の存続条件を課した
- **無駄の判決**: GUI $131有罪・playbooks注入は前倒し廃止・Notionはキャリア資産に分計・
  自己監査の计測は30日枠内のみ
- **あり方**: F'(証拠駆動の実行保証器+承認制台帳)を**期限付き**本線とし、
  B=能動的な税移管計画、C/E=12月の縮退先、D=実需(外部エージェント2種×3件)発生時のみ。
  上位目的は常にオーナーの時間と経験

一行で: **orghは「CCの再開発」をやめ、CCが払えない税(統治・監査・ローカル配達)だけを
払う会社になる。それでも12月に実需を示せなければ、畳む勇気を持つ。**

## 9. 整理サマリ(2026-08-21オーナー確認済み。機能仕分けと製品の三層)

### 9.1 機能の仕分け(判定原則: 予測でなくARCH-004——検証済み代替契約の実在で判定)

**① 移管待ち負債(力を入れない。CCが契約を満たしたら削除)**

| 機能 | 現状CCに無いもの | 移管の引き金 |
|---|---|---|
| 常駐watch・永続キュー | セッション独立の実行永続性 | CCバックグラウンド実行が永続性+再開契約を持ったら |
| lease・スリープ復帰・二重実行防止 | 実行の生死管理 | 同上(プラットフォームが持つべき層) |
| worktree編成・並列dispatch | —(Agent/Workflowがほぼ対応済み) | 移行試験に通り次第、最初の移管候補 |
| Planner/worker起動の配管 | —(headless claude -pのラッパー) | 同上 |
| GUI・可視化 | — | 凍結済み(追加投資なし) |
| playbooks自動注入 | —(CLAUDE.md/メモリ/スキルと重複) | **CCを待たず廃止確定**(次の窓) |
| 入力ソース配管(Notion等) | —(CC自身がMCPクライアント) | 追加ソースは作らない |

**② 残し続ける機能(CCが構造上払えない税。ただし12月の存続条件つき)**

1. **承認制の規範台帳**: 承認ゲート・supersede代謝・引用統計・版固定。CLAUDE.mdには統治
   (誰がいつ何を規範と認めたか)が無い
2. **独立検収の契約**: worker/Reviewerの構造的分離(買収防止)+構造化AC→証拠→裁定の型
3. **監査台帳(ledger)**: コスト・escape・verdict・全イベントの追記型正本=説明責任
4. **ローカルprivate領域への配達(copyback)**: manifest照合+原子コピー。CCクラウドは
   利用者マシンのgit外領域へ構造上到達できない
5. **停止意味論**: copyback_conflict・awaiting_human・外部承認待ち——「どう止まるか」の契約。
   プラットフォームは前進機能を作るが、止まり方の統治は利用者側の思想

### 9.2 製品の三層(層を混ぜると誇張になる。分けて持つ)

| 層 | マーケット | 目的 | ストーリー |
|---|---|---|---|
| **今日** | **n=1**(オーナーと、そのAIセッション群)。市場製品ではなく個人の実行保証層 | オーナーの可処分時間と望む経験(転職・生活・学習・楽しさ)の最大化 | — (自分に語る物語は不要。証拠だけ) |
| **今期** | **採用市場**(Notion=MCP実績 / Cognition=Devin統治層) | 動くポートフォリオとして応募を通す | 「エージェント統治を、語るのではなく実装して運用した人」。escape第1号の記録(自分の検収ミスを自分の計器が捕まえた一部始終)が最強の証拠物件 |
| **将来オプション** | **エージェント・ガバナンス**(実需=外部エージェント2種×各3件が観測されるまで昇格させない) | エージェントを信用可能にする統治層 | 「エージェントは強力になったが信用の装置がない。orghはACを満たすまで完遂させ、承認された規範で検収し、全過程を監査可能にする層。下のエンジンはCCでもDevinでもよい」 |

**一行**: orghは「実行エンジンの会社」ではなく「信用の会社」。今日はn=1、今期は履歴書、
いつか統治層——ただしどの層でも、**証拠が先で物語は後**。
