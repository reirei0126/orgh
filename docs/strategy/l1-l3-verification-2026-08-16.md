# L1/L3 手動検証の結果(2026-08-16)

direction-2026-08.md Phase 3事前検証(「exporterを作る前に、その仕事を1回人力でやる」)の実施記録。
対象: decision-os(実装リポ: decision-os-mvp)の実ケース 002-korea-honeymoon。
実施ミッション: 014f2a2a(整合性回復、7.7分想定→実績1タスク・validate 10→3エラー)。

## 発見(重要度順)

1. **【最重要・架構】git境界問題**: decision-osの実ケースは `private/`=git管理外(プライバシー境界)。
   orghの成果受け渡しモデル(worktree分離→branch commit→diff検収)は**git管理外の成果物領域では
   全て空振りする**: workerはケースを worktree に手動コピーして編集、`commit_task_result` は
   コミット対象なし、`git diff` 検収も不能、成果物はworktreeに取り残された(人力サルベージで回収)。
   → **A7/L2の設計入力**: 「成果物領域がgitでない実行対象」への受け渡し契約
   (成果物のマニフェスト+コピーバック or 直接書き込みの許可境界)が必要。
   これはontology-platform連携(実世界操作の結果はそもそもgitに無い)でも同型の問題になる

2. **【L3が本丸】台帳の腐り**: ACT-002は8/6に実質完了していたが、台帳は10日間 pending のまま
   (orghがA5で直した「嘘をつく状態」のdecision-os版)。書き戻し自体は3分で済む=
   **自動化の価値は速度ではなく「忘れないこと」**。L1(起票の自動化)よりL3(完了の書き戻し)の方が痛い

3. **【L1設計の前提修正】実仕事はACT台帳の外にあった**: 今回orghに流した価値ある仕事(整合性回復)は
   どのACTにも存在しない保守作業。**exporterがaction-plan.mdだけ読む設計では実仕事を拾えない**

4. **【誤情報の教訓】ノートの前提が切れていた**: 起票時の「5エラー」は `tail -8` による切り詰めで、
   実際は10エラーだった。workerは全量を発見してスコープを正しく判断した(ゲートも1回差し戻しで機能)。
   起票者(人間側)のエラー列挙より「バリデータexit 0」のような**機械的な完了条件**の方が頑健

5. **【需要は実在】**: 旅行ケースは能動運用中(HD-004=航空券決定あり、期日超過ACTあり)。
   ただし月間頻度はまだ不明

## 判定(direction-2026-08.md §8-4 に照らして)

- **L1(exporter)は急がない**: 手動変換の摩擦は小さく、ACT台帳だけでは実仕事を拾えないことも判明。
  設計をやり直すべき(起票対象=ACT+保守作業、機械的完了条件を正とする)
- **先に痛いのは**: ①git境界の受け渡し契約(A7設計に統合) ②L3方向の書き戻し(完了検知→台帳更新)
- 継続観測: 今後数ヶ月で同種の往復が月1件発生するかを見て、L1/L3の実装可否を再判定する
