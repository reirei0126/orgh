# orgh バリュー戦略設計書 — ペルソナ組織と判断基準層

作成: 2026-08-10(外出先playgroundセッションでの戦略壁打ちの決着)
状態: オーナーレビュー待ち

## 0. 前提となる決定(このセッションで確定)

| 論点 | 決定 |
|---|---|
| 誰のためのバリューか | **徹底的にセグメントA=オーナー自身**。自分のアイデア実現スループット最大化が第一。OSS評判(B)・商用(C)はその実績の副産物として後から狙う |
| 最大のボトルネック | 完走後の検収滞留(C)> アイデア供給(D)> 実行中の張り付き(B)> 投入前(A) |
| 検収滞留の原因 | **状況×信用の複合**。①判断がPC拘束前提で外出先から処理できない ②成果物の品質(特に完成度・磨き)がオーナー基準に大幅未達で、検収の腰が重い |
| アイデア供給難の原因 | 粒度(構想→ミッションへの分解層が無い)+発想(供給そのものが装置の処理能力に未達) |
| 品質ギャップの中身 | 仕様適合ではなく**完成度・磨き**(UI/UXの詰め)。機械ゲート合格とオーナー合格の断層 |
| 基準台帳の更新権 | **下書き+ワンタップ承認**(完全自動は基準汚染リスクで棄却。復活条件: 承認負荷が実測で問題化し、かつ巻き戻し運用が確立した場合) |

## 1. 診断: 価値方程式

```
実現された価値/週 = 投入ミッション数 × オーナー基準の合格率 × マージ・デプロイ到達率
                   ─────────────────────────────────────────
                          オーナー注意コスト(PC拘束時間)
```

現状は分子が3箇所で細り、分母が膨らんでいる。orghという「実行する組織」はできたが、
その周りに3つの機関が欠けている:

1. **美意識を持った品質幹部** — Reviewerはエンジニア視点の受け入れ条件しか見ておらず、
   オーナーの完成度基準を持たない(sikore-slot: 機械検証全合格でUI崩壊が通過)
2. **外から動かせる社長室** — 投入・状態確認・検収・マージの4接点が全てPC拘束
3. **構想を仕込む企画室** — orghはintent記述後しか担当せず、壁打ち・分解の上流が空白

### 差別化価値の認識

実行の配管(並列起動・resume・worktree)はコモディティ化していく
(claude -p+リモート操作で代替可能)。orghの differentiation は
**多角的視点で決断・調整する組織性**と**playbookで賢くなる学習ループ**の側にしか築けない。
ペルソナ構想は追加機能ではなく、存在理由の回収である。

## 2. 戦略の3本柱

### 柱1: ペルソナ検収ゲート(主戦・最優先)

計画・実行・レビューという役割粒度に加え、**ペルソナ粒度**
(消費者・デザイナー・セールス・マーケ・敵対チーム等)を組織に導入する。
第1弾は品質断層に直撃する**消費者+デザイナーの2ペルソナを検収ゲートに**置く。

**設計原則(絶対規範): ペルソナは「別視点のプロンプト」では機能しない。
「別の証拠チャネル」を持って初めて機能する。**
- 消費者ペルソナ: 実ブラウザ/スクリーンショットで成果物に触れて評価する
- デザイナーペルソナ: 視覚成果物(スクショ・録画)に対して完成度基準で裁定する
- プロンプトだけの人格分けは同じLLMが自分に頷くだけになる(sikore-slot教訓の一般化)

因果: オーナー基準との落差が縮む → 検収が「読んで数分」に軽くなる → 滞留が解け
マージ到達率が上がる → 価値方程式の分子が太る。

成立条件: ペルソナレビューのコスト増(+数USD/ミッション)を合格率向上が上回ること。
2〜3ミッションで実測検証する。

### 柱2: 判断基準層(背骨)

ペルソナ全員が参照する判断基準を、オーナーの資産として外部化する。

1. **基準台帳** — `criteria/*.md`(デザイン/プロダクト/投資基準…)。
   1エントリ = ID + 原則 + 由来(どの裁定から生まれたか)+ 強度(絶対規範/選好)。
   ただのMarkdown+git管理なので、オーナーはいつでも直接編集できる
2. **自動成長ループ** — 検収・承認・差し戻しのたびにRetroがオーナー判断と理由を蒸留し、
   台帳への**差分下書き**を生成。オーナーがスマホからワンタップで承認/修正/棄却。
   例: sikore-slot裁定は `DESIGN-001: 視覚検証なしの合格を信用しない` として載るべきだった
3. **双方向性(反論する組織)** — ペルソナは裁定時に基準IDの引用義務を負う。
   オーナーの新要望が既存基準と矛盾したら、実行前に
   「PROD-003と矛盾します。改定しますか、例外にしますか」と議論を開始する。
   オーバーライドはそれ自体が新しい判例として蒸留される

既存の原型: playbooks(運用教訓)と docs/audit/pruning-ledger.md(オーナー裁定台帳)。
基準台帳は判断の一般原則、playbookは作業のやり方、と役割を分ける。

### 柱3: 社長室(モバイル・オーナー接点/運用先行で並走)

4つのオーナー接点(投入・状態確認・検収・マージ判断)を外出先スマホから数分で
処理できるようにする。**外出先のClaudeセッション(このplayground)が既にプロトタイプ**であり、
GUI第2期を待たず運用で先取りする:
- 完了報告は自己完結文書(掘らずに判断できる材料一式+スクショ+プレビューURL)
- awaiting_approval / 検収待ち をプッシュ通知
- approve・検収裁定・基準台帳の差分承認をセッション経由で実行

「作る」より「使い方を決める」に近い。柱1と独立に今日から改善できる。

## 3. decision-osとの関係(被りではなく積層)

- **decision-os** = 重大な一回性判断のプロセスOS(証拠・構造化推論・敵対レビュー・明示承認)。
  低頻度・高セレモニー。価値観は各ケースへの入力であり、蓄積機構を持たない
- **orgh判断基準層** = 日常の高頻度裁定に使う憲法+判例集。高頻度・低セレモニー

接続: **判例集で捌けない新規争点・重大判断はdecision-os手続きへエスカレーションし、
裁定結果が新しい判例として基準台帳へ還流する**(裁判所と判例集の関係)。

## 4. 実行順序と検証

1. **柱2の最小版**(基準台帳の器+検収裁定からの下書き生成)—— ペルソナが引用する基準が
   先に無いと柱1が一般論レビューに堕ちるため、薄く先行
2. **柱1第1弾**(消費者+デザイナーペルソナを検収ゲートへ、実ブラウザ/スクショ必須)
3. **柱3は運用で即日並走**(自己完結報告様式・通知・セッション検収の運用ルール化)
4. 企画室(壁打ち→分解の上流ペルソナ会議)・セールス/マーケ/敵対ペルソナは
   検収の信用回復後に着手 —— 上流を先に太らせると滞留が悪化するため

### 成功指標(既存ops reportの拡張)

- **オーナー基準一発合格率**(機械合格率ではなく、オーナー検収での一発合格)
- **検収リードタイム**(ミッション完走→マージ/デプロイ判断までの時間)
- **オーナー接点のスマホ完結率**
- 基準台帳のエントリ数と、ペルソナ裁定における引用率

### GUI投資の事後検証(視点を捨てない)

「claude -p+リモコンで足りた説」は反証可能な問いとして保持する。
検証: 柱3運用が確立した時点で、GUI経由/セッション経由のオーナー接点利用比率を1週間計測し、
GUI第2期のスコープ判断(続行/縮小)の材料にする。

## 5. スコープ外(今回やらないこと)

- セールス・マーケ・敵対チームペルソナの実装(配置は上流整備時に設計)
- GUI第2期の実装着手(PRDは存在するが、柱3の運用実測を先に)
- B(OSS)/C(商用)向けの施策一切
