# orgh 方向性と機能の取捨(2026-08-15)

> 目的: orghが「何になるのか」を定め、機能を **①追加/修正する ②他プロダクトに任せる ③劣後・捨てる**
> の3つに分類する。判断の根拠は `harness-landscape-2026-08.md`(競争環境・反証調査済み)と
> criteria台帳 ARCH-001/002(上半分/下半分の境界)。
>
> 前提となる問い(オーナー): 「orghはプロダクト開発だけでなく色々なアクションを実行できたらいい。
> ontology-platform や decision-os と連携したらいいのか?」

---

## 1. orghの定義(何であって、何でないか)

**orgh = 受け入れ条件を満たすまで、人間・AI・外部実行系による仕事を検収駆動で完遂させる制御層。**

("執行機関"では実行基盤・スケジューリング・実世界操作まで所有する含意になり、本文の委譲方針と矛盾する。
"品質保証層"はDAG・差し戻し・人間割当を落とすので狭い。"執行OS"は下半分を抱えるので広い。)

- **である**: 受け入れ条件を満たすまで反復する実行ループ / その判断を規範として蓄積・代謝する台帳 /
  人間を含むワーカーの割り当てと状態管理 / 実行の監査記録
- **でない**: エージェント実行基盤(=Claude Code等の土台) / 意思決定の枠組み(=decision-os) /
  実世界システムへの型付き操作(=ontology-platform) / 汎用ワークフローエンジン(=n8n/Temporal)

**境界の切り方**: 「決める/触る」では切れない(orgh自身もPlannerがDAGとACを決め、workerがブランチや
文書を直接変更する)。正しい三分割は **目的・価値判断の妥当性(前段) / 成果物の適合性(orgh) /
外部システムへの確定的副作用の許可(後段)**。

## 2. 三層アーキテクチャ(既存資産の連携)

オーナーの問い「色々なアクションを実行したい」への答えは、**orghに機能を足すことではなく、
後段(ontology-platform)を繋ぐこと**である。

```
┌─────────────────────────────────────────────────────────────┐
│ decision-os          「何をやるか」を決める                    │
│  証拠収集 → 構造化推論 → 敵対的レビュー → 不確実性の明示        │
│  → 人間承認 → 実行可能なnext action                          │
│  出力: 決定スナップショット + next actions                    │
└───────────────────────────┬─────────────────────────────────┘
                            │ next action = ミッションノート
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ orgh                 「決まったことをやりきる」                 │
│  計画(DAG) → 並列実行 → 検収ゲート → 差し戻し → 教訓/規範化     │
│  ワーカー: AI(claude/codex) + 人間(awaiting_human)            │
│  出力: 成果物(ブランチ/文書) + ledger(実測) + criteria(規範)   │
└───────────────────────────┬─────────────────────────────────┘
                            │ 実世界への副作用を伴う操作
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ ontology-platform    「実世界のシステムに安全に触る」           │
│  型付きドメイン定義 + SafetyRegistry/decideGate(HITL承認)      │
│  + コネクタ(Postgres/CSV/…) + Executor/Reconciler            │
│  出力: 実システムへの適用結果 + 実行記録                       │
└─────────────────────────────────────────────────────────────┘
```

**この分業の要点**: 3つとも「人間承認ゲート」を持つが、**守る対象が違う**。
decision-os=**目的・価値判断の妥当性**、orgh=**成果物の適合性**、ontology-platform=**副作用の許可**。
**それぞれのゲートを相手に押し付けない**ことが設計の肝(orghのReviewerに目的の是非を裁定させない)。

### 連携の具体(実装順)

| # | 連携 | 形 | 効果 |
|---|---|---|---|
| L1 | decision-os → orgh | 決定snapshot の next action を、ミッションノート形式で vault へ書き出す(decision-os側のexporter) | 「決めたのに動かない」の解消。orghは無改造 |
| L2 | orgh → ontology-platform | **worker種別 `ontology`** を新設。タスクの成果を「型付きアクションの適用」として ontology CLI(`apply`)へ渡す。副作用の承認は ontology の decideGate に委ねる | orghが独自コネクタを持たずに実世界操作へ到達。安全境界は既存資産を再利用 |
| L3 | orgh → decision-os | **Reviewerは決定の是非を裁定しない**。「現ACでは完遂不能」「前提が反証された」という**証拠付きエスカレーション**のみを出力し(新feedback種別 `ESCALATE:`)、decision-os のcase起票と決定の見直しは人間/decision-os側が行う | 3層のフィードバックループが閉じる。かつorghが目的の妥当性判断に踏み込まない |

**重要**: L2の実装は「orghにコネクタを書く」ではなく「orghにアダプタ1本を足す」。
Gmail/Slack/SaaS等への個別対応は **すべて ontology-platform 側のコネクタとして実装する**
(でなければorghが無限にインテグレーションを抱える)。

## 3. 機能の分類

### 3.1 追加/修正する(orghの本体 = 上半分)

優先順。◎は競争環境分析で「残る差別化」と特定された領域。

| # | 機能 | 理由 | 規模 |
|---|---|---|---|
| A1 | **人間接点イベントの標準化と配送保証**(`approval.requested` / `human_task.requested` / `mission.completed` 等のイベント定義 + 拒否理由の還流契約 + 汎用webhook配送)。Slack/push等の**個別配送先は外部アダプタ/MCPへ委譲** | 人間ノードは実装済みだが**気づけない**ので機能していない。ただしSlack直結を本体に入れると3.2「個別インテグレーションを作らない」の自己例外になるため、orghが持つのはイベント契約と配送保証まで | 小 |
| A2 | **worker権限プリセット**(読み取りgit等を事前承認。実測済み: b6503b9a t3で人間依頼に化けた) | 誤ったawaiting_human転換を減らす=人間の時間を守る | 小 |
| A3 | ◎ **criteria台帳の実効性強化**: **基準ごとの適用履歴・競合・失効候補の表示**(どの基準が何回効いたか、矛盾する基準はどれか、使われていない基準はどれか) / 「一時的 vs 恒久」の選別指針 | 代謝(差別化点)を機能させるには腐敗の観測が要る。**注: 台帳の閲覧・承認UIは `#/criteria` に実装済み**(CriteriaPage.tsx)。不足しているのは"効いているかの観測"であって閲覧手段ではない | 中 |
| A4 | ◎ **検収器のベンチマーク**(既知の合否ペアで検収の精度を測る。Qodo流のF1) | **orghの最大の盲点**: 検収の質を測る手段が無い。「検収に通った」の価値が測定できていない | 中 |
| A5 | 状態表示の ledger/procreg 突合(「嘘をつくUI」一族の解消) | 監査可能性(強み)の土台が嘘をついている | 中 |
| A6 | ◎ **AC記法の標準化**(EARS等の型を Planner のプロンプトに導入し、検収可能性を機械的に担保) | 品質バー問題への実務的アプローチ。DESIGN-005(実物観察→正解仕様→TC)と接続 | 中 |
| A7 | **製品非依存の `action` 実行契約**(入力スキーマ / dry-run / 承認待ち / 適用結果 / 冪等性キー / 補償可否 を定義したworker種別)。ontology-platformはその**最初のアダプタ**であって型に固定しない | 「色々なアクション」への回答。`ontology` を型として固定するとARCH-002違反(製品への密結合)になり、実行系を差し替えた瞬間にorgh本体へ他製品の型が残る | 中 |
| A8 | モデルルーティング(役割×難易度で安価モデルへ) | コスト構造の改善。実測基盤(ledger)があるので効果検証できる | 中 |

### 3.2 他プロダクト/土台に任せる(自分で作らない)

| 機能領域 | 委譲先 | 根拠 |
|---|---|---|
| エージェント実行基盤・並列制御・プロセス隔離・スケジューリング | **Claude Code等の土台** | ARCH-001。既存のqueue/slots/watcherは「いずれ捨てる橋」 |
| ツール接続の標準化 | **MCP** | 2026年の事実上の標準。独自adapter拡張より委譲 |
| 実世界システムへの型付き操作・コネクタ・副作用の安全ゲート | **ontology-platform** | 既に SafetyRegistry/decideGate/Executor/Reconciler がある。orghが再実装するのは重複 |
| 意思決定の枠組み(証拠・不確実性・価値判断・敵対的レビュー) | **decision-os** | orghの検収は「成果物の品質」であって「決定の妥当性」ではない。混ぜると両方壊れる |
| サンドボックス実行・egress制御 | **土台 or コンテナ基盤**(将来: OpenHands型の隔離、または土台のsandbox機能) | 自前実装は大きすぎる。脅威モデルに正直に書き続けることが当座の誠実さ |
| PRレビューの一般的品質チェック(bug/security/style) | **CodeRabbit/Qodo等** | 商用が圧倒的に洗練。orghの検収は「受け入れ条件の充足」に特化すべき |
| チーム機能(SSO/SCIM/監査エクスポート/権限管理) | **作らない**(必要ならDevin等の商用) | 単一オーナー前提が設計の強み。多人数対応は別プロダクト |

### 3.3 劣後・捨てる

| 対象 | 判断 |
|---|---|
| デスクトップGUIの機能拡張 | **凍結**。現状維持で運用可能。CLIとvaultが主戦場であり、GUIに投資しても差別化にならない |
| 下半分への新規投資(queue/slots/watcherの高機能化) | **禁止**(ARCH-001)。土台が同等機能を出したら削除・委譲 |
| リモート実行・クラウドworker | **必要になるまで着手しない**。単一マシンの制約が実害を出してから |
| 独自のインテグレーション(Gmail/Slack/Notion等への直接対応) | **作らない**。通知(A1)だけは例外で、それ以外はontology-platform側のコネクタとして実装 |
| プラグイン機構・エコシステム構築 | **時期尚早**。ユーザーが自分1人の段階で拡張点を設計しても仮説が検証できない |

## 4. 実行順(推奨)

**Phase 1: 制御層の正当性を回復する(小〜中・最優先)** — **A5状態表示の真実性** + A1イベント契約 + A2権限プリセット。
A5を先頭に置く理由: 監査可能性が定義の中核である以上、**状態表示が嘘をついている限り通知も人間ノードも
監査記録も信用できない**(21時間ゾンビ表示・実行中なのに全pending表示の実例あり)。
通知元の状態が正しくなって初めてA1が意味を持つ。UX改善ではなくP0。

**Phase 2: 差別化点を測れるようにする(中)** — A4検収ベンチマーク + A3台帳の実績追跡。
**「検収と台帳が本当に効いているのか」を数字で言えるようにする**。これができると、
以後の改善が推測でなく実測ドリブンになる。orghの実測主義とも一貫する。

**Phase 3: 越境する(中)** — A7 ontology worker + L1 decision-os連携。
「色々なアクション」の実現。三層が繋がる。

**Phase 4: 品質バーへの挑戦(中〜大)** — A6 AC記法 + DESIGN-005の標準工程化。
世界の誰も解けていない領域なので、ここでの半歩が最大の差別化になる。

A8(モデルルーティング)は独立しているので合間に差し込む(A4の実測基盤ができた後が望ましい。
効果を数字で確認できるため)。

## 5. この方針が誤りうる点(自己批判)

- **Phase 2の前提**: 「検収の質は測れる」と仮定しているが、正解ラベル(既知の合否ペア)を
  作るコスト自体が高い可能性がある。最初は小さく(10ケース程度で)試すべき
- **三層連携の複雑性**: 3プロダクトの結合は運用負荷を増やす。L1(ファイル出力)のような
  疎結合から始め、密結合は避ける
- **単一オーナー前提の賞味期限**: 公開・他者利用が視野に入った瞬間、3.2の「作らない」判断の
  いくつか(サンドボックス・権限管理)は覆る。その時は本ドキュメントを改訂する
