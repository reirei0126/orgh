# orgh 方向性と機能の取捨(2026-08-15)

> 目的: orghが「何になるのか」を定め、機能を **①追加/修正する ②他プロダクトに任せる ③劣後・捨てる**
> の3つに分類する。判断の根拠は `harness-landscape-2026-08.md`(競争環境・反証調査済み)と
> criteria台帳 ARCH-001/002(上半分/下半分の境界)。
>
> 前提となる問い(オーナー): 「orghはプロダクト開発だけでなく色々なアクションを実行できたらいい。
> ontology-platform や decision-os と連携したらいいのか?」

---

## 1. orghの定義(何であって、何でないか)

**orgh = 受け入れ条件を満たすまで、人間・AI・外部実行系による仕事を検収駆動で完遂させる制御層。**

("執行機関"では実行基盤・スケジューリング・実世界操作まで所有する含意になり、本文の委譲方針と矛盾する。
"品質保証層"はDAG・差し戻し・人間割当を落とすので狭い。"執行OS"は下半分を抱えるので広い。)

- **である**: 受け入れ条件を満たすまで反復する実行ループ / その判断を規範として蓄積・代謝する台帳 /
  人間を含むワーカーの割り当てと状態管理 / 実行の監査記録
- **でない**: エージェント実行基盤(=Claude Code等の土台) / 意思決定の枠組み(=decision-os) /
  実世界システムへの型付き操作(=ontology-platform) / 汎用ワークフローエンジン(=n8n/Temporal)

**境界の切り方**: 「決める/触る」では切れない(orgh自身もPlannerがDAGとACを決め、workerがブランチや
文書を直接変更する)。正しい三分割は **目的・価値判断の妥当性(前段) / 成果物の適合性(orgh) /
外部システムへの確定的副作用の許可(後段)**。

## 2. 三層アーキテクチャ(既存資産の連携)

オーナーの問い「色々なアクションを実行したい」への答えは、**orghに機能を足すことではなく、
後段(ontology-platform)を繋ぐこと**である。

```
┌─────────────────────────────────────────────────────────────┐
│ decision-os          「何をやるか」を決める                    │
│  証拠収集 → 構造化推論 → 敵対的レビュー → 不確実性の明示        │
│  → 人間承認 → 実行可能なnext action                          │
│  出力: 決定スナップショット + next actions                    │
└───────────────────────────┬─────────────────────────────────┘
                            │ next action = ミッションノート
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ orgh                 「決まったことをやりきる」                 │
│  計画(DAG) → 並列実行 → 検収ゲート → 差し戻し → 教訓/規範化     │
│  ワーカー: AI(claude/codex) + 人間(awaiting_human)            │
│  出力: 成果物(ブランチ/文書) + ledger(実測) + criteria(規範)   │
└───────────────────────────┬─────────────────────────────────┘
                            │ 実世界への副作用を伴う操作
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ ontology-platform    「実世界のシステムに安全に触る」           │
│  型付きドメイン定義 + SafetyRegistry/decideGate(HITL承認)      │
│  + コネクタ(Postgres/CSV/…) + Executor/Reconciler            │
│  出力: 実システムへの適用結果 + 実行記録                       │
└─────────────────────────────────────────────────────────────┘
```

**この分業の要点**: 3つとも「人間承認ゲート」を持つが、**守る対象が違う**。
decision-os=**目的・価値判断の妥当性**、orgh=**成果物の適合性**、ontology-platform=**副作用の許可**。
**それぞれのゲートを相手に押し付けない**ことが設計の肝(orghのReviewerに目的の是非を裁定させない)。

### 連携の具体(実装順)

**前提の訂正(2026-08-15 Codexレビューr3)**: 初版は「decision-osのsnapshotを書き出すだけ・orghは無改造」
としていたが、両プロダクトの実装を確認した結果**いずれも事実誤認**だった。以下は実装を読んだ上での契約案。

#### L1: decision-os → orgh(**双方に新規実装が必要**)

- **正本はsnapshotではない**。`decision-snapshot.md` は派生表示でactionは最大3件。
  正本は `action-plan.md` の **ACTエントリ**(dependencies / Done when / Owner を持つ)
- decision-os側に**新規exporter**が要る(現状はvalidator+fixturesであり、export/起票CLIは存在しない)
- 交換形式は**version付きJSON/YAML**を正準とする(snapshotの文章解析は禁止):
  `case_id / action_id / revision / task / deliverable / dependencies / done_when / owner / decision_id`
- orgh側にも**新規実装が要る**: `(source_system, source_case_id, source_action_id)` の**一意制約**と
  **revisionの単調増加検査**(でないと、期限や説明の更新で同じACTが再着火する。
  現在の処理済み判定は本文hashなので内容が変われば再着火してしまう)
- ファイル書き込みは**一時ファイル+rename**の原子的操作(watcherの途中読み取りによる誤計画を防ぐ)

#### L2: orgh → 外部実行系(**状態機械の契約が必須**)

- **FATAL回避**: `ontology apply` は承認が必要な場合 `PENDING` の execution をJSON出力して**正常終了**する。
  現在のorghはworker終了後にReviewerが検収して合格なら即 `done` にするため、
  **未実行の操作を完了扱いする**。承認後の実行結果を受け取ってタスクを再開する状態も無い
- 最低限必要な機械状態契約:
  `planned → approval_requested → executing → succeeded | rejected | expired | failed | unknown`
- `PENDING` では**Reviewerを呼ばず** `awaiting_external_approval` へ遷移させる(新ステータス)。
  承認後の**再開通知またはpoll契約**を定義する(でないと永久に待つ)
- **正本の所在**: 副作用の記録はontology側のexecutionが正本、orghのledgerは**参照(execution_id)を持つだけ**。
  二重台帳の照合責任はorgh側(不一致検知)に置く

#### L3: orgh → decision-os(**構造化された差し戻し**)

- Reviewerは決定の是非を裁定しない。「現ACでは完遂不能」「前提が反証された」を
  **証拠付きの構造化エスカレーション**(新feedback種別 `ESCALATE:`)として出力する
- 人間可読の文字列を増やすだけではループにならない。エスカレーションは
  **L1の交換形式のキー(`source_case_id` / `source_action_id` / `revision`)を保持**した機械可読レコードとし、
  decision-os側がcaseの再検討トリガとして消費できる形にする

**規模感の訂正**: 「Gmail/Slack/SaaS等はすべて ontology-platform 側のコネクタとして実装」は
現状資産の過大評価だった(現在あるのは Postgres / CSV コネクタのみ)。正しくは
**「orghは個別接続を持たない」という原則のみを維持**し、実際にどの実行系へ繋ぐかは
そのつど判断する(ontology-platformは有力な第一候補だが、SaaS接続の実装は未着手の別工数)。

## 3. 機能の分類

### 3.1 追加/修正する(orghの本体 = 上半分)

優先順。◎は競争環境分析で「残る差別化」と特定された領域。

| # | 機能 | 理由 | 規模 |
|---|---|---|---|
| A1 | **人間接点イベントの標準化と配送保証**(`approval.requested` / `human_task.requested` / `mission.completed` 等のイベント定義 + 拒否理由の還流契約 + 汎用webhook配送)。Slack/push等の**個別配送先は外部アダプタ/MCPへ委譲** | 人間ノードは実装済みだが**気づけない**ので機能していない。ただしSlack直結を本体に入れると3.2「個別インテグレーションを作らない」の自己例外になるため、orghが持つのはイベント契約と配送保証まで | 小 |
| A2 | **worker権限プリセット**(読み取りgit等を事前承認。実測済み: b6503b9a t3で人間依頼に化けた) | 誤ったawaiting_human転換を減らす=人間の時間を守る | 小 |
| A3 | ◎ **criteria台帳の実効性強化**: **基準ごとの適用履歴・競合・失効候補の表示**(どの基準が何回効いたか、矛盾する基準はどれか、使われていない基準はどれか) / 「一時的 vs 恒久」の選別指針 | 代謝(差別化点)を機能させるには腐敗の観測が要る。**注: 台帳の閲覧・承認UIは `#/criteria` に実装済み**(CriteriaPage.tsx)。不足しているのは"効いているかの観測"であって閲覧手段ではない | 中 |
| A4 | ◎ **検収の逃し(escape)監視 + sentinel回帰**(汎用F1ベンチマークではない。詳細は§3.4) | **orghの最大の盲点**: 検収の質を測る手段が無い。ただし汎用ベンチマークは費用対効果が悪いため方式を縮小(r4指摘) | 小〜中 |
| A5 | 状態表示の ledger/procreg 突合(「嘘をつくUI」一族の解消) | 監査可能性(強み)の土台が嘘をついている | 中 |
| A6 | ◎ **ACの構造化**(最小版: AC ID・検証方式・期待証拠の3点を機械可読にする。完全なEARS導入は後続) | 品質バー問題への実務的アプローチ。**A4より先に必要**: ACの粒度が未定義だと「成果物の欠陥」と「ACが要求していない事項」を区別できず、検収の偽陰性を誤計上する(r4指摘) | 中 |
| A7 | **製品非依存の `action` 実行契約**(入力スキーマ / dry-run / 承認待ち / 適用結果 / 冪等性キー / 補償可否 + L2の状態機械)。**認証境界**: LLM workerには認証情報を渡さず、orghの**非LLM action runner**が固定argvでCLIを起動する。domain/config/principalは**管理者設定**から解決し、action定義やLLM生成文字列からは取らない(params はargv配列/stdin/fileで渡す) | 「色々なアクション」への回答。製品名を型に固定するとARCH-002違反。**認証境界を明記しないと、秘密stripの回避=LLMへ副作用権限を丸ごと渡すことになる**(r3指摘) | 中 |
| A8 | モデルルーティング(役割×難易度で安価モデルへ) | コスト構造の改善。実測基盤(ledger)があるので効果検証できる | 中 |

### 3.4 検収の質をどう測るか(A4の設計・r4レビューで方式を縮小)

**却下した案**: 「Qodo流のF1で汎用ベンチマーク」。理由は3つ。
①Qodoの実測は成果物全体の合否分類ではなく**100PRへ580個の欠陥を注入してissue単位でP/R/F1**を出したもので、
「既知の合否ペア」への読み替えは誤り。②既存runs/ledgerから正解ラベルは抽出できない
(23ミッション・Reviewer判定141件に対し独立したowner verdictは9件、しかも粒度がReviewer=task /
owner=missionで一致しない)。③成果物種別(コード/UI/文書)ごとに欠陥注入と固定ケース保守が必要で、
単一オーナーには継続コストが重すぎる。

**採用する案(低コストから順に)**:

1. **escape(逃し)の記録**: owner verdictで「機械ゲート通過後に不合格」となった事例を
   `escape` として全件記録する。これが**最重要指標**(誤受入)の母集団になる
2. **抜き打ち再検収**: 完走ミッションの約20%をownerが独立に再検収する(標本抽出)
3. **sentinel回帰ケース**: 過去の実害事例5〜10件(UI崩壊・事実誤認・前提破綻など)を
   固定ケース化し、検収器の変更前後で**同一ケースをshadow replay**する
4. **拡張は実害ドリブン**: 誤受入が再発したドメインに限って欠陥注入セットを追加する

**主指標(F1ではない)**: ゲートの損失は非対称なので、
**①誤受入率**(gold不合格なのに合格。最重要) **②誤差戻し率**(gold合格なのに不合格)
**③欠陥カテゴリ別Recall**(UI目視・仕様不整合・テスト不足…) **④追加コスト**(検収時間・トークン費・不要な再実装回数)。
ペルソナとownerの一致率は**補助指標に留める**(両者が同じ誤りをしても一致率は上がるため、正確性を示さない)。

**必要なデータ契約**(現在の `task.review` はtask IDとpass/failしか持たず改善点を特定できない):
`case_id` / `gold_issue_id` / 対象AC / 欠陥カテゴリ / Reviewer finding / 根拠 /
prompt・model・criteriaの版 / 判定 / 費用。改善の採否は**同一固定ケースのshadow replay**で
「どの変更がどのカテゴリのRecallを上げ、誤差戻しをどれだけ増やしたか」を見て決める。

**pilotの扱い**: 最初の10ケースは**基盤が動くかの確認**であり、**性能値は公表・比較しない**
(1件で率が10ポイント以上動くため)。本評価は欠陥あり/なし各30件程度+信頼区間、成果物種別ごとに分けて出す。

### 3.2 他プロダクト/土台に任せる(自分で作らない)

| 機能領域 | 委譲先 | 根拠 |
|---|---|---|
| エージェント実行基盤・並列制御・プロセス隔離・スケジューリング | **Claude Code等の土台** | ARCH-001。既存のqueue/slots/watcherは「いずれ捨てる橋」 |
| ツール接続の標準化 | **MCP** | 2026年の事実上の標準。独自adapter拡張より委譲 |
| 実世界システムへの型付き操作・コネクタ・副作用の安全ゲート | **ontology-platform** | 既に SafetyRegistry/decideGate/Executor/Reconciler がある。orghが再実装するのは重複 |
| 意思決定の枠組み(証拠・不確実性・価値判断・敵対的レビュー) | **decision-os** | orghの検収は「成果物の品質」であって「決定の妥当性」ではない。混ぜると両方壊れる |

## 4. 実行順(推奨)

**Phase 1: 制御層の正当性を回復する(小〜中・最優先)** — **A5状態表示の真実性** + A1イベント契約 + A2権限プリセット。
A5を先頭に置く理由: 監査可能性が定義の中核である以上、**状態表示が嘘をついている限り通知も人間ノードも
監査記録も信用できない**(21時間ゾンビ表示・実行中なのに全pending表示の実例あり)。
通知元の状態が正しくなって初めてA1が意味を持つ。UX改善ではなくP0。

**Phase 2: 差別化点を測れるようにする(中)** — **A6最小版(AC ID・検証方式・期待証拠の構造化)→
A4 escape監視+sentinel(§3.4)→ A3台帳の実績追跡**の順。
A6を先に置く理由: ACの粒度と記法が未標準のままでは「成果物の欠陥」と「ACが要求していない事項」を
区別できず、検収の偽陰性を誤計上する(r4指摘)。ラベルの単位だけは先に固定する必要がある。
**「検収と台帳が本当に効いているのか」を数字で言えるようにする**のがこのPhaseの目的。

**Phase 3: 越境する(中〜大)** — A7 action実行契約(L2の状態機械+認証境界を含む) + L1 decision-os連携。
「色々なアクション」の実現。**ただし初版の想定より重い**: L1はdecision-os側の新規exporterと
orgh側の一意制約が要り、L2は `awaiting_external_approval` 新ステータスと再開契約が要る(§2)。
最小の一歩は「dry-runのみのactionアダプタ1本」で、承認・再開の契約はその次。

**Phase 4: 品質バーへの挑戦(中〜大)** — A6 AC記法 + DESIGN-005の標準工程化。
世界の誰も解けていない領域なので、ここでの半歩が最大の差別化になる。

A8(モデルルーティング)は独立しているので合間に差し込む(A4の実測基盤ができた後が望ましい。
効果を数字で確認できるため)。

## 5. この方針が誤りうる点(自己批判)

- **Phase 2の前提**: 「検収の質は測れる」と仮定している。r4レビューで汎用ベンチマークは
  費用対効果が悪いと判明したため escape監視+sentinel へ縮小した(§3.4)。それでも
  **escapeの母集団はowner verdictの実施率に依存する**(現在9件のみ)ため、
  抜き打ち再検収を運用に載せられなければこの測定自体が成立しない
- **三層連携の複雑性**: 3プロダクトの結合は運用負荷を増やす。r3レビューで
  「L1は疎結合で軽い」という初版の見立ては誤りと判明した(双方に新規実装が必要)。
  **連携の価値がその実装コストに見合うかは未検証**であり、Phase 3着手前に
  「decision-osのACTが実際に何件orghへ流れるのか」を手動で1〜2件試して見極めるべき
- **単一オーナー前提の賞味期限**: 公開・他者利用が視野に入った瞬間、3.2の「作らない」判断の
  いくつか(サンドボックス・権限管理)は覆る。その時は本ドキュメントを改訂する
