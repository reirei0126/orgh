## 1. orghの定義(何であって、何でないか)

**orgh = 受け入れ条件を満たすまで、人間・AI・外部実行系による仕事を検収駆動で完遂させる制御層。**

("執行機関"では実行基盤・スケジューリング・実世界操作まで所有する含意になり、本文の委譲方針と矛盾する。
"品質保証層"はDAG・差し戻し・人間割当を落とすので狭い。"執行OS"は下半分を抱えるので広い。)

- **である**: 受け入れ条件を満たすまで反復する実行ループ / その判断を規範として蓄積・代謝する台帳 /
  人間を含むワーカーの割り当てと状態管理 / 実行の監査記録
- **でない**: エージェント実行基盤(=Claude Code等の土台) / 意思決定の枠組み(=decision-os) /
  実世界システムへの型付き操作(=ontology-platform) / 汎用ワークフローエンジン(=n8n/Temporal)

**境界の切り方**: 「決める/触る」では切れない(orgh自身もPlannerがDAGとACを決め、workerがブランチや
文書を直接変更する)。正しい三分割は **目的・価値判断の妥当性(前段) / 成果物の適合性(orgh) /
外部システムへの確定的副作用の許可(後段)**。

**「外部副作用」の定義(初版は広すぎて既存workerのコード変更まで違反扱いになっていた)**:
後段へ委譲するのは **orghが管理する成果物領域(worktree/vault/runs)の外にある、業務SoR・
外部通信・決済・アカウント・インフラに対する確定操作**に限る。
**worktree内のコード変更・文書生成・git操作・テスト実行はorgh workerの責任**であって、A7の対象外。

## 2. 三層アーキテクチャ(既存資産の連携)

オーナーの問い「色々なアクションを実行したい」への答えは、**orghに機能を足すことではなく、
後段(ontology-platform)を繋ぐこと**である。

```
┌─────────────────────────────────────────────────────────────┐
│ decision-os          「何をやるか」を決める                    │
│  証拠収集 → 構造化推論 → 敵対的レビュー → 不確実性の明示        │
│  → 人間承認 → 実行可能なnext action                          │
│  出力: 決定スナップショット + next actions                    │
└───────────────────────────┬─────────────────────────────────┘
                            │ next action = ミッションノート
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ orgh                 「決まったことをやりきる」                 │
│  計画(DAG) → 並列実行 → 検収ゲート → 差し戻し → 教訓/規範化     │
│  ワーカー: AI(claude/codex) + 人間(awaiting_human)            │
│  出力: 成果物(ブランチ/文書) + ledger(実測) + criteria(規範)   │
└───────────────────────────┬─────────────────────────────────┘
                            │ 実世界への副作用を伴う操作
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ ontology-platform    「実世界のシステムに安全に触る」           │
│  型付きドメイン定義 + SafetyRegistry/decideGate(HITL承認)      │
│  + コネクタ(Postgres/CSV/…) + Executor/Reconciler            │
│  出力: 実システムへの適用結果 + 実行記録                       │
└─────────────────────────────────────────────────────────────┘
```

**この分業の要点**: 3つとも「人間承認ゲート」を持つが、**守る対象が違う**。
decision-os=**目的・価値判断の妥当性**、orgh=**成果物の適合性**、ontology-platform=**副作用の許可**。
**それぞれのゲートを相手に押し付けない**ことが設計の肝(orghのReviewerに目的の是非を裁定させない)。

### 連携契約の三方向(**L番号は順序を示さない**。唯一の実装順は §4 Phase 3 に集約する)

**前提の訂正(2026-08-15 Codexレビューr3)**: 初版は「decision-osのsnapshotを書き出すだけ・orghは無改造」
としていたが、両プロダクトの実装を確認した結果**いずれも事実誤認**だった。以下は実装を読んだ上での契約案。

#### L1: decision-os → orgh(**双方に新規実装が必要**)

- **正本はsnapshotではない**。`decision-snapshot.md` は派生表示でactionは最大3件。
  正本は `action-plan.md` の **ACTエントリ**(dependencies / Done when / Owner を持つ)
- decision-os側に**新規exporter**が要る(現状はvalidator+fixturesであり、export/起票CLIは存在しない)
- **リポジトリの特定**: 本節の「decision-os」は実装リポジトリ **`~/projects/decision-os-mvp`**
  (origin: `decision-os.git`)を指す。`~/projects/decision-os/` は実装前のhandoffパッケージであり、
  validator/fixtures/ケース実装を持たない(混同するとL1の前提が再現できない)
- 交換形式は**version付きJSON/YAML**を正準とする(snapshotの文章解析は禁止)。
  **正準フィールド名(L1/L3/A1in/一意制約で完全に統一する。初版は `case_id` と `source_case_id` が
  混在しており、双方が文書どおり実装しても接続できなかった)**:
  `source_system / source_case_id / source_action_id / source_revision` +
  `task / deliverable / dependencies / done_when / owner / decision_id`
- orgh側にも**新規実装が要る**: **三要素 `(source_system, source_case_id, source_action_id)` の一意制約**と、
  **同一三要素内での `source_revision` 単調増加検査**(でないと、期限や説明の更新で同じACTが再着火する。
  現在の処理済み判定は**ノートファイル全体のSHA-256先頭16桁**なので、内容が変われば再着火してしまう)
- ファイル書き込みは**一時ファイル+rename**の原子的操作(watcherの途中読み取りによる誤計画を防ぐ)

#### L2: orgh → 外部実行系(**状態機械の契約が必須**)

- **FATAL回避**: `ontology apply` は承認が必要な場合 `PENDING` の execution をJSON出力して**正常終了**する。
  現在のorghはworker終了後にReviewerが検収して合格なら即 `done` にするため、
  **未実行の操作を完了扱いする**。承認後の実行結果を受け取ってタスクを再開する状態も無い
- 最低限必要な機械状態契約:
  `planned → approval_requested → executing → succeeded | rejected | expired | failed | unknown`
- `PENDING` では**Reviewerを呼ばず** `awaiting_external_approval` へ遷移させる(新ステータス)。
  承認後の**再開通知またはpoll契約**を定義する(でないと永久に待つ)
- **正本の所在**: 副作用の記録はontology側のexecutionが正本、orghのledgerは**参照(execution_id)を持つだけ**。
  二重台帳の照合責任はorgh側(不一致検知)に置く

#### L3a: orgh → decision-os(**完遂不能の構造化差し戻し**)

- Reviewerは決定の是非を裁定しない。「現ACでは完遂不能」「前提が反証された」を
  **証拠付きの構造化エスカレーション**(新feedback種別 `ESCALATE:`)として出力する
- 人間可読の文字列を増やすだけではループにならない。エスカレーションは
  **L1の正準キー(`source_system` / `source_case_id` / `source_action_id` / `source_revision`)を保持**した
  機械可読レコードとし、
  decision-os側がcaseの再検討トリガとして消費できる形にする

#### L3b: orgh → decision-os(**完了状態の還流**)

- ミッション完了を出どころ(`source_*`)付きで前段の台帳へ書き戻す方向。
  §4 Phase 3b' の `writeback_pending` 状態機械で「書き戻し忘れ」を構造的に防ぐ
  (2026-08-16検証: ACT-002の完了が10日間台帳未反映の腐りを実測。**L1よりこちらが痛い**)

**規模感の訂正**: 「Gmail/Slack/SaaS等はすべて ontology-platform 側のコネクタとして実装」は
現状資産の過大評価だった(現在あるのは Postgres / CSV コネクタのみ)。正しくは
**「orghは個別接続を持たない」という原則のみを維持**し、実際にどの実行系へ繋ぐかは
そのつど判断する(ontology-platformは有力な第一候補だが、SaaS接続の実装は未着手の別工数)。

## 3. 機能の分類(2軸: **所有先** × **移行状態**)

初版は「追加/委譲/捨てる」の3分類だったが、投資対象・将来の所有先・凍結が混在し、
**既存機能を「当面維持する橋」「代替確認後に削除」「即時廃止」のどれにするか決められない**
という欠陥があった(r2指摘)。以下は所有先と移行状態の2軸で書き直したもの。

### 3.0 下半分の再定義(r6のFATAL指摘を受けた修正)

初版の ARCH-001「下半分(配管)には投資しない」は、**未確認の将来予測(土台が同等機能を出す)を
設計原則に昇格させ、かつ信頼性の修復まで禁じていた**。実際には下半分の不備が上半分の正当性を
直接破壊した/しかけた実例がある(キュー投入失敗によるノート損失、inode競合、21時間のゾンビ表示)。
なお「watch再起動による実行中断」は**危険が確認されただけで事故としては未発生**
(2026-08-12のセッションログでは3回の切替をいずれも無事故で実施)。

**正しい切り方は「配管かどうか」ではなく「実行メカニズム/制御意味論」**:

| 区分 | 内容 | 所有 |
|---|---|---|
| **実行メカニズム** | スレッド/プロセス管理、ファイルロックの実装、スケジューラの実体、隔離手段 | **委譲可**(土台・アダプタの背後へ隔離) |
| **制御意味論** | 「どのタスクをいつ再開できるか」「重複実行をどう防ぐか」「人間・外部承認待ちをどう永続化するか」「ledgerとの原子的遷移」 | **orghが所有**(土台に任せても消えない。`awaiting_human`/`awaiting_external_approval`/差し戻し/予算はorgh固有) |

→ **ARCH-001/002は改訂が必要**(§6。2026-08-15にARCH-003/004として承認・改訂完了)。
出口は「queue/slots/watcherを丸ごと捨てる」ではなく「**土台依存部分をアダプタの背後へ隔離する**」。

### 3.4 検収の質をどう測るか(A4の設計・r4レビューで方式を縮小)

**却下した案**: 「Qodo流のF1で汎用ベンチマーク」。理由は3つ。
①Qodoの数値(自社ブログ公表であり第三者の独立検証ではない)は成果物全体の合否分類ではなく
**100PRへ580個の欠陥を注入してissue単位でP/R/F1**を出したもので、
「既知の合否ペア」への読み替えは誤り。②既存runs/ledgerから正解ラベルは抽出できない
(**2026-08-15時点で `runs/*/mission.json` 23件、全 `ledger.jsonl` の `task.review` 141件に対し
`mission.owner_verdict` は9件**。しかも粒度がReviewer=task / owner=missionで一致しない)。③成果物種別(コード/UI/文書)ごとに欠陥注入と固定ケース保守が必要で、
単一オーナーには継続コストが重すぎる。

**採用する案(r5でさらに縮小。単一兼業オーナーに維持可能な範囲へ)**:

1. **【今やる】escape(逃し)の記録**: owner verdictを運用で必須化し、「機械ゲート通過後に不合格」と
   なった事例を `escape` として**全件記録**する。記録・集計は自走可能

   ⚠ **この指標だけで「誤受入率」は測れない**(r8のFATAL): verdictの無い機械合格は未評価のままで、
   **見逃しが多いほど発見されない**という選択バイアスがある(現状23ミッション中verdict 9件、
   しかも `orgh verdict` は任意実行で完了を阻止しない)。最悪の筋書きは
   「通知がbest-effortで落ちる→verdictされない→escapeゼロ→品質良好と誤認→A9も永遠に着火しない」。
   よって **Phase 2の完了条件を `verdict取得率 ≥ 90%` + 少量でよいので無作為抽出した独立再検収**とする。
   抽出を運用に載せられない場合は、**指標名を「報告済みescape件数」に落とし、
   この値で品質の良否やA9の要否を判断してはならない**と明記する
2. **【条件付き】sentinel回帰**: escapeが実際に発生した領域に限り、その事例を固定ケース化して
   検収器の変更前後で shadow replay する(最初から5〜10件揃えようとしない)
3. **【小さく固定枠で】独立再検収**: 「毎月最大N件(暫定3件)」の固定上限で無作為抽出して再検収する。
   Phase 2完了条件の一部だが、**20%のような比率指定にはしない**(ミッション数に比例して負荷が増えるため)
4. **【当面やらない】** 比率指定の抜き打ち再検収 / 成果物種別ごとに各30件の統計評価 /
   汎用の欠陥注入セット。**初期構築が「大」+恒常運用が「毎ミッションの20%」になり維持不能**
   (gold判定と欠陥分類は自走させられない=人間工数が線形に増える)

**主指標(F1ではない)**: ゲートの損失は非対称なので、
**①誤受入率**(gold不合格なのに合格。最重要) **②誤差戻し率**(gold合格なのに不合格)
**③欠陥カテゴリ別Recall**(UI目視・仕様不整合・テスト不足…) **④追加コスト**(検収時間・トークン費・不要な再実装回数)。
ペルソナとownerの一致率は**補助指標に留める**(両者が同じ誤りをしても一致率は上がるため、正確性を示さない)。

**必要なデータ契約**(現在の `task.review` はtask IDとpass/failしか持たず改善点を特定できない):
`case_id` / `gold_issue_id` / 対象AC / 欠陥カテゴリ / Reviewer finding / 根拠 /
prompt・model・criteriaの版 / 判定 / 費用。改善の採否は**同一固定ケースのshadow replay**で
「どの変更がどのカテゴリのRecallを上げ、誤差戻しをどれだけ増やしたか」を見て決める。

**pilotの扱い**: 最初の10ケースは**基盤が動くかの確認**であり、**性能値は公表・比較しない**
(1件で率が10ポイント以上動くため)。本評価は欠陥あり/なし各30件程度+信頼区間、成果物種別ごとに分けて出す。

## 4. 実行順(r5でPhase構成を現実的な規模へ再編)

**Phase 0: 前提の是正(人間・小)【完了 2026-08-15】** — **ARCH-001/002の改訂ドラフトをオーナーが承認する**(§6)。
現行の原則のままでは「下半分の信頼性修復」が禁止扱いになり、Phase 1のA5と矛盾する。

**Phase 1: 制御層の正当性を回復する(小〜中・最優先)** — **A5状態表示の真実性** → A1out(縮小版)+A10最小 → **A2限定版**。
**A2限定版の範囲を確定する**: 「能力不足を `awaiting_human` へ誤りなく遷移させる契約と、その監査記録」まで。
実行ファイルhash・filesystem/network制約の宣言は**記録情報でありセキュリティ保証ではない**と明記して分離し、
強制可能な土台(sandbox等)が入るまで完全版には進まない(完全版は別Phase・大規模扱い)。
A5を先頭に置く理由: 監査可能性が定義の中核である以上、**状態表示が嘘をついている限り通知も人間ノードも
監査記録も信用できない**(21時間ゾンビ表示・実行中なのに全pending表示の実例)。通知元の状態が
正しくなって初めてA1が意味を持つ。

**Phase 2: 測れるようにする(中)** — **A6最小版(AC ID・検証方式・期待証拠+criteria版固定)** →
**A4(owner verdict必須化+escape全件記録)** → A3a(利用統計)。
A6を先に置く理由: ACの粒度が未定義だと「成果物の欠陥」と「ACが要求していない事項」を区別できず、
検収の偽陰性を誤計上する。**統計評価はこのPhaseの目標に含めない**(§3.4)。

**Phase 3: 越境する(2026-08-16 手動検証の結果を反映して全面改訂)**

手動検証(`l1-l3-verification-2026-08-16.md`)により初版の設計前提が3つ覆った:
①実ケースは `private/`=**git管理外**であり、orghのworktree→branch受け渡しが全て空振りする
②L1(起票の自動化)より**L3(完了の書き戻し)が痛い**(ACT-002が10日間pending腐り)
③実仕事はACT台帳の外にも存在する(exporterがaction-plan.mdだけ読む設計では不足)

改訂後の構成(優先順):

- **3a': 非git成果物の受け渡し契約(A7へ統合・最優先)** — 契約本文(r11反映):
  - **staging限定実行**: workerにはorgh管理のstaging領域(worktree)だけを渡す。対象領域への
    直接書き込み防止は**現状は強制できない**(sandbox/filesystem強制が無い)ため、本契約は
    「防止」ではなく**検知の暫定運用**: コピーバック時に宛先の事前hashと突合し、worker実行中に
    宛先が変化していたら `copyback_conflict` として停止・人間裁定(**セキュリティ保証ではない**)
  - **成果物manifest**: workerは「相対パス・種別・サイズ・SHA-256」の一覧を出力。
    **orghが検収開始時に再計算してstagingを凍結**し、コピー直前・後にも再検証する。
    パスは正規化し対象ルート内に閉包(絶対パス・`..`・symlink・未列挙ファイルは拒否)
  - **copybackの原子性**: 同一filesystemなら一時ディレクトリへ全量配置→検証→rename/swap。
    不可ならファイル単位journalで再開可能に。途中失敗は `copyback_partial` として**doneにしない**。
    再実行は「コピー済みhash一致はskip、不一致は自動上書き禁止・人間裁定」。
    コピー開始前に宛先hashを記録し、利用者編集との競合を検知する
- **3b': L3識別子付与 + writeback_pending(「L3最小実装」から改称・r11反映)** —
  best-effortイベントにメタデータを載せるだけでは忘却経路(通知落ち・見落とし・更新前の
  プロセス死)が全て残るため、最低限の状態機械を持つ:
  ① 完了時に `writeback_pending` を**永続記録**(ledger+未処理一覧)
  ② 未処理は ack されるまで `orgh status`/未裁定一覧で**再提示し続ける**
  ③ 人間が前段の台帳を更新したら `orgh writeback-ack <mission>` で完了
  ④ **webhook成功を完了条件にしない**。台帳の自動更新(full L3)は頻度データが揃ってから
- **3c': L1 exporterは凍結** — 手動変換の摩擦は小さく(15分/件)、月間頻度も未実証。
  再検討条件: 手動変換が**月3件**を超えたとき。その際は起票対象をACT+保守作業に広げ、
  人間のエラー列挙ではなく**機械的な完了条件**(validator exit 0等)を正とする設計にする

段階ゲート・クラッシュ契約・部分導入の負債設計(旧3a/3b/3cに定義済みのもの)は3a'/3b'にも適用する。
**Phase 4は削除。** 代わりに**着手条件付きのA9**とする: 「Phase 2のescape記録で、
**目視品質起因のescapeが一定件数(暫定3件)発生した場合のみ**、A9(実物観察ベースの検収工程)を
オーナー主導で設計する」。AC標準化自体はKiro等の既成領域であり、orghが独自に工程化する価値は
**実害が観測されてから**判断する。

**A10(内部SPI)** は2段階に分ける(初版は「アダプタを増やす直前」としながらPhase 1で
webhookアダプタを足す計画で自己矛盾していた): **A10最小版**(`error taxonomy` / `idempotency` /
`API version` の3点)を**Phase 1のA1outと同時**に定義し、**完全版**(`capabilities` / `config schema` /
`lifecycle`)は**2本目のアダプタ(=Phase 3aのaction)を足す直前**に定義する。
