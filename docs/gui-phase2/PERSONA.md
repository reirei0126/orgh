# orgh GUI第2期 ペルソナ・セグメント定義

本ドキュメントは `docs/gui-phase2/INVENTORY.md`(GUI第1期実装インベントリ)を事実の根拠として、GUI第2期が誰のために作られるかを1人のペルソナに絞って定義する。オーナー裁定により、主対象は「Claude Code等のCLIツールに慣れた開発者」であり、ITに不慣れな層は今回スコープ外(ただし将来判断材料として障壁リストを別掲する)。

## 1. 主対象ペルソナ(1枚)

### 呼称

「ターミナル常駐の開発者」(オーナー本人像)

### 技術背景(普段使うツール・端末環境)

- 日常的にターミナル(zsh等のシェル)を開きっぱなしにして作業し、Claude Code・Codex等のCLIエージェントツールを日次で使用している。
- macOS環境での利用を前提にできる(INVENTORY.md §6「検証環境: macOS 15.5 / Apple M4」、GUI自体もmacOS向け`.app`バンドルとして検証されている)。
- `git`のブランチ・worktree・コミットの概念を理解しており、`orgh`が内部で`worktree.enabled`時にworktree/ブランチを使う(INVENTORY.md §1 C11)ことも違和感なく扱える。
- YAML設定ファイル(`config.yaml`)を直接編集できる。GUIの`SettingsPage`が扱うのは`orghBin`/`configPath`/`runsDir`の3フィールドのみで、`roles`/`workers`/`prompts_dir`等のYAML本体はGUI対象外だが(INVENTORY.md §5)、本ペルソナはこれをエディタで直接編集することに抵抗がない。

### orghを使う目的とジョブ

- 複数のミッション(CLI能力`run`/C8、INVENTORY.md §1)を並行して走らせ、「今どれが動いていて、どれが止まっていて、どれに承認が要るか」を素早く把握したい(Jobs to be done: 状況把握の高速化)。
- ターミナルのスクロールバックに埋もれがちな`events`/`status`(C6/C10)の情報を、目視で追いやすい形(進捗バー・StatusBadge・DependencyGraph、INVENTORY.md §3)で確認したい。
- 承認(`approve`/C13)・キャンセル(`cancel`/C12)のような「待たれている操作」を、コマンドを打たずワンクリックで済ませたい。

### 1日の使い方(朝・日中・夜のシナリオ)

- **朝**: コーヒーを淹れながらGUIのミッション一覧(MissionListPage)を開き、夜間~早朝に走らせていたミッションのStatus列(`done`/`failed`/`awaiting_approval`/`running`等、INVENTORY.md §2.1 `_derive_status`)とCost列を10秒ポーリング(`LIST_POLL_MS = 10_000`、INVENTORY.md §3)でざっと確認する。`awaiting_approval`があれば詳細画面に飛んで承認する。
- **日中**: 新しいタスクを思いついたら新規ミッション画面(NewMissionPage)からintentを直接入力して`run`を起動し(INVENTORY.md §3)、他の作業をしながらミッション詳細画面(MissionDetailPage)を別タブで開いてDependencyGraphとLiveLog(5秒ポーリング、`DETAIL_POLL_MS = 5_000`)を横目で追う。自己改変ガード等で`awaiting_approval`になったら都度承認する。
- **夜**: その日動かした複数ミッションのコスト($)を振り返りたいが、GUIには期間集計レポート(`report`/C7)の導線が無い(INVENTORY.md §4)ため、必要であればターミナルに戻り`orgh report --days 1`を直接叩く。GUIとCLIを併用することに抵抗はない。

### 既に自力でできること(=GUIが肩代わりしなくてよいこと)

- `orgh scan`/`orgh watch`をターミナルから直接叩いてvault監視デーモンを常駐させる操作(GUI未対応、INVENTORY.md §4 C1/C2「なし」)。
- `orgh gc`によるplaybook統合・runsアーカイブ(GUI未対応、INVENTORY.md §4 C4「なし」)。
- `orgh resume --retry-failed`での失敗タスク再開、`orgh cleanup`でのworktree/ブランチ掃除(いずれもGUI未対応、INVENTORY.md §4 C9/C11「なし」)。
- `config.yaml`のYAML本体(`roles`/`workers`/`prompts_dir`)の直接編集(GUIのSettingsPageは接続設定3項目のみを扱う、INVENTORY.md §5)。
- `orgh doctor --json`の生出力を読んで`worker:<name>`/`role:<role>`チェックの意味を解釈すること(INVENTORY.md §2.4)。

### 苦痛に感じること

- `configPath`等の既定値が相対パス(`config.yaml`)でGUIプロセスのcwd依存のため、絶対パスを自分で調べて再入力しないと動かない(INVENTORY.md §5「VERIFY.mdでは...実機検証時に絶対パスへ事前投入する運用を取った」)。CLIに慣れているとはいえ、GUIごとにこの手順を再現するのは手間である。
- ミッション詳細のライブログ`tail`が100固定でUI側から変更できない(INVENTORY.md §4 C6備考)。長時間ミッションで直近100件より前の文脈を追いたい時に不便。
- `--no-retro`のようなCLIで使えるフラグがGUIのNewMissionPageからは指定できない(部分的対応、INVENTORY.md §4 C8)。GUIでできることとCLIでできることの範囲がずれている。
- 一覧画面のポーリングが10秒固定、詳細画面が5秒固定(INVENTORY.md §3)で、集中して見ている時に更新が遅く感じたり、他作業中は逆に頻繁すぎたりする。

### このペルソナにとっての「良いGUI」の定義

1. **状態がひと目でわかる**: StatusBadge・進捗バー・Cost/Budget統計(INVENTORY.md §3 MissionDetailPage)のように、ターミナルでコマンドを打たなくても今の状態が視覚的に即座に読み取れること。
2. **次にできる操作しかボタンが活性化されない**: `awaiting_approval`のときだけ承認ボタンが、`running`/`awaiting_approval`のときだけキャンセルボタンが活性化する(INVENTORY.md §3)ように、迷わせる余地のあるボタンを常時押せる状態にしないこと。
3. **失敗時に次の行動への導線がある**: 一覧取得失敗時に設定画面へのリンクボタンが出る(INVENTORY.md §3 MissionListPage)ように、エラーで終わらせず次の一手を示すこと。
4. **CLIでできることとGUIでできることのギャップを隠さない**: `scan`/`watch`/`gc`/`report`/`resume`/`cleanup`のようにGUI未対応の機能がある場合(INVENTORY.md §4)、それを暗黙のうちに「無いものとして振る舞う」のではなく、CLIで補える設計のまま矛盾なく共存させること。
5. **嘘をつかない**: 表示されている状態(Status/Cost/Attempts等)が常に実データ由来であること。第1期はブラウザ単体実行時に`mocks.ts`へ自動フォールバックする(INVENTORY.md §3)仕組みを持つが、今どちらのモードで表示しているか本人に紛れがないこと。

## 2. 主対象ペルソナから見た成功状態

- **セットアップ**: `orghBin`/`configPath`/`runsDir`を一度絶対パスで入力し「orgh doctor を実行」で全チェックが`ok:true`になった時点(INVENTORY.md §2.4, §5)で、以後このペルソナが二度と同じ入力をやり直さずに済んでいれば成功。
- **利用開始**: 初めてNewMissionPageからintentを入力してミッションを起動し、MissionDetailPageのStatusBadge・DependencyGraph・LiveLogだけを見て「今何が起きているか」をターミナルの`events`/`status`コマンドに戻らずに説明できる状態になっていれば成功。
- **利用熟練**: 複数ミッションを並行運用しながら、GUIとCLI(`report`/`resume`/`cleanup`等の未対応領域)を意識的に使い分け、GUIの一覧・詳細画面を「毎日最初に見る場所」として自然に習慣化していれば成功。

## 4. 今回スコープ外とする理由と、将来広げるときの再検討トリガー

### スコープ外とする理由

- オーナー裁定により、第2期は「Claude Code等のCLIツールに慣れた開発者が毎日使って気持ちいいこと」を最優先とする。この層はB-01〜B-10の障壁の大半(絶対パス入力、YAML編集、CLIコマンドの直接実行、git worktree概念、ターミナル常駐操作)を自力で回避・解決できるため、これらを今解消しても主対象ペルソナの体験改善に直結しない。
- B-02(YAML編集UI)やB-09(認証・利用者分離)のように「大」判定の項目は、GUI設計そのものの前提(単一ユーザー・ローカルプロセス)を変える規模の変更であり、狭めた主対象への「迷わない・嘘をつかない・次にやることが見える」改善(1章「良いGUIの定義」)より優先度が構造的に低い。
- 障壁リストは切り捨てではなく、将来セグメントを広げる判断のための棚卸しとして本ドキュメントに保持する。

### 将来広げるときの再検討トリガー

- 主対象ペルソナ(CLI慣れした開発者)向けのGUI改善が一巡し、「迷わない・嘘をつかない・次にやることが見える」の観点で新規の未対応項目が枯渇したとき。
- オーナー以外の利用者(非開発者)への配布・招待が具体的に発生し、B-01(絶対パス入力)やB-10(Gatekeeper警告)のようなインストール段階の障壁が実際に利用開始を妨げる事例が観測されたとき。
- 複数人での同時利用(共有PC・チーム運用)が実際に必要になり、B-09(認証・利用者分離の欠如)が実害(誤承認・意図しないキャンセル等)として顕在化したとき。
- B-04(scan/watch)のような常駐監視をGUI経由で使いたいという要望が、CLIに不慣れな利用者から具体的に上がったとき。
