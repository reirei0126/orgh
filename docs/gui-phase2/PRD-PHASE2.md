# orgh GUI第2期 PRD

## 1. 背景と第2期のゴール

第1期(未マージブランチ `orgh/8e096d63/t4`)は、CLI全13サブコマンド(`INVENTORY.md` 1章 C1〜C13)のうち `list`/`status`/`events`/`doctor`/`cancel`/`approve` の6つを完全に、`run`(`--intent`/`--note`のみ、`--no-retro`非対応)を部分的にGUI化した。ミッション一覧・新規起動・詳細(StatusBadge・DependencyGraph・LiveLog)・設定(接続3項目+doctor)の4画面が動作し、`VERIFY.md`によれば実データ(過去ミッション8件)での疎通・`pytest`166件・`cargo test`17件が全て成功している。

一方で `GAP-ANALYSIS.md` は、ライフサイクル3段(セットアップ/利用開始/利用熟練)×品質特性2種(機能の有無/user friendliness)の6セルで28件のギャップ(G-01〜G-28)を特定した。特に深刻度「高」の8件は次の3種類に大別できる。

1. **GUIが実態と食い違う表示をする(嘘をつく)**: `doctor`の`worker:*`チェックがバイナリ疎通(`--version`)のみで認証状態を見ておらず「全OK」が実態と食い違う(G-07)。「runsディレクトリ」設定フィールドはCLI呼び出しに一切渡らない表示専用キャッシュなのに、実際に効く`orghBin`/`configPath`と同列のフォームに見える(G-06)。
2. **初めての成功体験に到達できない**: ノートの書き方・`#go`・`projects_map`の説明がGUI内に一切無い(G-10)。
3. **日常運用の中で必ずCLIに戻される**: キャンセル直後に再開(`resume`)する手段がGUIに無い(G-20)、`report`(週次合格率・コスト集計)を見る手段が無い(G-17)、retro/playbookの中身が見えない(G-18)、複数ミッション横断のコスト俯瞰が無い(G-22)。

第2期のゴールは、オーナー裁定の対象ユーザー(`PERSONA.md`)である「Claude Code等のCLIツールに慣れた開発者」にとって、上記の「嘘をつく」表示と「日常運用の直後の穴」を解消し、`PERSONA.md` 1章が定義する「良いGUI」の5原則(状態がひと目でわかる/次にできる操作しかボタンが活性化されない/失敗時に次の行動への導線がある/CLIとGUIのギャップを隠さない/嘘をつかない)への適合度を高めることである。新機能の網羅的な追加ではなく、タスク仕様が示す原則「user friendly is best(機能追加より迷わない・嘘をつかない・次にやることが見えるを優先)」に沿った取捨選択を行う。

## 2. 対象ユーザーと成功指標

対象ユーザーは `PERSONA.md` が定義する「ターミナル常駐の開発者」1名(オーナー本人像)。日常的にターミナルを開きっぱなしにし、Claude Code・Codex等のCLIエージェントを日次で使用し、`git`のworktree/ブランチ概念やYAML直接編集に抵抗がない。非IT層は今回のスコープ外(`PERSONA.md` 3章・4章)。

`PERSONA.md` 2章が定義する3段階の「成功状態」を、以下の観測可能な指標に落とす。

### セットアップの成功指標
- SettingsPageの`orghBin`/`configPath`/`runsDir`を一度絶対パスで保存した後、同一マシン・同一設定ディレクトリ(Tauriの`app_config_dir()`配下`settings.json`、`INVENTORY.md` §5)を使う限り、同じ値を再入力する操作が発生しない。
- 「orgh doctor を実行」の結果、`doctor_payload()`の`ok`が`true`になる(`INVENTORY.md` §2.4)。かつ、その`ok:true`が実際のミッション実行時のワーカー認証エラーと矛盾しない(第3章 P0-1で扱う)。
- [要検証: 実測時間データなし] 初回セットアップに要する所要時間。

### 利用開始の成功指標
- 初めてNewMissionPageからintentまたはnoteでミッションを起動し、MissionDetailPageのStatusBadge・DependencyGraph・LiveLogのみを見て、ミッションの最終状態(`done`/`failed`/`awaiting_approval`のいずれか)まで説明できる。
- ミッション起動時のエラー(ノート未検出等)が発生した場合、onErrorバナーの文言だけで次に取るべき行動(ノート名の修正方法等)が判断できる。
- [要検証: 現状GUI・CLI双方に「GUIのみで完結したか」を計測する手段が無い] 初回ミッション完走までにターミナルへ切り替えた回数。

### 利用熟練の成功指標
- 複数ミッションを並行run中、一覧画面のポーリング間隔(`LIST_POLL_MS = 10_000`、`INVENTORY.md` §3)内でStatus/Cost列が実データと一致し続ける。
- `report`/`resume`/`cleanup`等のGUI非対応領域についてCLIへ切り替える際、GUI側の表示(ミッションID・ステータス・コスト)とCLI側の出力に矛盾が無い。
- [要検証: 利用頻度データなし] GUIを「毎日最初に見る場所」として起動する頻度(週あたり日数)。

## 3. スコープ項目(優先度順)

### [P0-1] 診断結果を実態に一致させる(doctorのworker認証チェック)
- **解決するギャップ**: G-07
- **なぜこの優先度か**: `doctor`の「全OK」表示は、対象ペルソナが毎日最初に見るセットアップ健全性の唯一の判断材料である(`PERSONA.md` 2章「セットアップの成功状態」)。バイナリ疎通のみで認証状態を見ないまま「OK」と表示するのは、良いGUI定義5「嘘をつかない」に正面から反し、実行時になって初めて認証エラーで失敗するという最悪の裏切りを生む(`GAP-ANALYSIS.md`が「嘘をつくUIの典型例」と明記)。
- **やること**:
  - `worker:<name>`チェックが、バイナリ疎通(`--version`)だけでなく、実際にAPI呼び出しが可能な認証状態を可能な範囲で検証する(検証方法はワーカーCLIごとに異なりうるため実装時に個別調査する)。
  - 認証確認ができない・未対応のワーカー種別については、「疎通OK・認証状態は未確認」であることをdetail文言で明示し、無条件の「OK」表示にしない。
  - SettingsPageの診断結果テーブルで、疎通チェックと認証チェックを視覚的に区別できるようにする。
- **受け入れ基準**:
  - 認証切れ状態のワーカーに対して`doctor`を実行すると、`worker:<name>`のdetailに認証状態が疎通確認とは別に表示される。
  - 認証確認が技術的に不可能なワーカー種別では、「疎通OKのみ確認・認証未確認」である旨がdetailに明記され、単なる「OK」とは表示上区別できる。
  - 認証済み・疎通OKのワーカーでは、従来通り「OK」と表示される(回帰無し)。
  - 実アプリを起動して、認証済み/未認証の少なくとも2状態でSettingsPageの診断結果表示を目視確認し、スクリーンショットを残す。
  - 既存の`pytest tests/ -q`(`INVENTORY.md` §6、第1期時点166件成功)が本変更後も成功する。
- **依存・前提**: 第1期ブランチのmainマージ後に着手。CLI側の変更が必要(`orgh/doctor.py` `_check_binary()`/`_binaries()`)。各ワーカーCLI(`claude`/`codex`等)の認証状態確認手段は実装時に個別調査が必要で、ワーカー種別によっては実現できない可能性がある。

### [P0-2] 「runsディレクトリ」設定の実態を機能フィールドと区別する
- **解決するギャップ**: G-06
- **なぜこの優先度か**: 良いGUI定義5「嘘をつかない」に直結する。ユーザーが値を変更・保存しても実際のCLI呼び出し(`build_run_args`/`run_json`/`run_sync`、`GAP-ANALYSIS.md` G-06根拠)には一切反映されないにもかかわらず、実際に効く`orghBin`/`configPath`と全く同じ見た目のフォームに並んでいるため、「設定したのに反映されない」という原因不明のバグ体験を生む。
- **やること**:
  - `runsDir`フィールドが「表示用のキャッシュであり、実際の参照元は`config.yaml`の`runs_dir`である」ことを、ホバー時ヒントだけでなく常時表示のUI要素で明示する。または、`runsDir`の値を実際のCLI呼び出しに反映させる(いずれの対応方針を取るかは実装時に決定する)。
  - 「表示用キャッシュのまま残す」場合は、`orghBin`/`configPath`(実際にCLI呼び出しに使われる)とは異なる視覚的区分(セクション分け・注記アイコン等)を設ける。
- **受け入れ基準**:
  - SettingsPage上で、`runsDir`フィールドが`orghBin`/`configPath`と同一の視覚的スタイルでは表示されない(区分される)、または実際にCLI呼び出しへ反映されるようになる。
  - `runsDir`の実際の挙動(反映される/されない)についての説明文言が、ホバーしなくても画面上に常時見える位置に存在する。
  - 実装方針(表示区分のみ/実挙動反映)のいずれを選んでも、既存の`orghBin`/`configPath`の保存・doctor実行フローに回帰が無い。
  - 実アプリを起動してSettingsPageを目視確認し、変更前後の表示差分が分かるスクリーンショットを残す。
- **依存・前提**: 第1期ブランチのmainマージ後に着手。「実挙動へ反映する」方針を選ぶ場合はCLI側(`orgh/cli.py`の各サブコマンドが`--runs-dir`相当の上書き引数を受け付けるようにする)変更が必要。「表示区分のみ」の場合はRust/フロントエンド側(`desktop/src-tauri/src/settings.rs`, `desktop/src/pages/SettingsPage.tsx`)のみで完結する。方針決定はオーナー確認が必要(第5章参照)。

### [P0-3] キャンセル後の再開(resume)をGUIから実行できるようにする
- **解決するギャップ**: G-20
- **なぜこの優先度か**: `PERSONA.md`「orghを使う目的とジョブ」で承認・キャンセルは「ワンクリックで済ませたい」日常操作と位置づけられている。GUIの「キャンセル」ボタンを押した直後、そのミッションを再開する手段がGUI内に存在せず、まさに直前にGUI操作を行ったタイミングでCLIに依存させられる(`GAP-ANALYSIS.md`「承認・キャンセルと並ぶ日常操作の直後に穴がある」)。CLI(`orgh resume mission_id --retry-failed`、`INVENTORY.md` C9)は既に実装済みのため、GUI側の実装コストに対して得られる連続性の改善が大きい。
- **やること**:
  - MissionDetailPageで、ステータスが再開可能な状態(キャンセル済み等)のミッションに対して「再開する」操作を提供する。
  - 「失敗タスクも含めて再試行する」(CLIの`--retry-failed`相当)を選べるようにする。
  - 再開後、ステータスが`running`へ遷移することを既存のポーリング(`DETAIL_POLL_MS = 5_000`)で反映する。
- **受け入れ基準**:
  - キャンセル済みミッションの詳細画面に「再開する」操作が表示され、他の状態(`done`/`running`等)では表示されない、または非活性である。
  - 「再開する」を実行すると、対象ミッションのステータスが`running`または対象タスクが`pending`へ遷移したことが画面上で確認できる。
  - 「失敗タスクも再試行する」を選んだ場合と選ばなかった場合とで、再開されるタスクの範囲が異なる。
  - 再開操作を実行できない状態(既に`running`中等)で誤操作した場合、エラーではなく操作自体が提示されない(良いGUI定義2「次にできる操作しかボタンが活性化されない」)。
  - 実アプリでキャンセル→再開の一連の流れを目視確認し、スクリーンショットを残す。
- **依存・前提**: 第1期ブランチのmainマージ後に着手。CLI側の追加実装は不要(`orgh resume`は実装済み)。Rustブリッジ(`desktop/src-tauri/src/commands.rs`)への新規Tauriコマンド追加とフロントエンド(`MissionDetailPage.tsx`)への操作追加が必要。

### [P0-5] エラーメッセージのわかりやすい言い換え
- **解決するギャップ**: G-08, G-14
- **なぜこの優先度か**: 日中の運用でノート名の指定ミスや接続設定不備は起こりやすく、その都度CLIの生エラー文字列(`note 'xxx' not found`等)や原因不明の定型文言が表示されると、原因切り分けの摩擦がユーザーに転嫁される。良いGUI定義3「失敗時に次の行動への導線がある」に対する不足を埋める。
- **やること**:
  - 一覧画面の取得失敗バナーで、原因(orgh未検出/config構文エラー/vaultパス不正等)をエラー内容から可能な範囲で判別し、原因別の次のアクション案内を出す。判別できない場合は現状通り生エラーメッセージも併記する。
  - note指定モードでノートが見つからない場合、CLIの生例外メッセージをそのまま出す代わりに「ノートが見つかりません。ノート名の綴りを確認するか、vault内の実ファイル名と照合してください」等の日本語説明に置き換え、生メッセージは折りたたみ等で参照可能にする。
- **受け入れ基準**:
  - config構文エラー・orgh未検出・vaultパス不正の少なくとも2種類のエラーで、一覧画面のバナー文言が異なる(原因ごとに区別されている)。
  - note未検出エラー発生時、バナーの主要文言が日本語の平易な説明になっており、生のCLI例外文字列は主要文言とは別枠(詳細表示等)に配置されている。
  - 判別できないエラーについては、従来通り生エラーメッセージが表示され、情報が失われない。
  - 実アプリで意図的にノート未検出エラーと設定不備エラーを発生させ、バナー表示を目視確認してスクリーンショットを残す。
- **依存・前提**: 第1期ブランチのmainマージ後に着手。CLI側の変更は必須ではない(フロントエンドでのエラー文字列パターンマッチで対応可能)が、将来的にCLI側が構造化エラーコードを返すようにすると判別精度が上がる(本第2期では前提としない)。

### [P1-2] report相当のGUI表示(週次合格率・差し戻し率・worker別失敗率)
- **解決するギャップ**: G-17
- **なぜこの優先度か**: 「増幅」(組織が賢くなっているか)を裏付ける定量指標として重要度は高いが、`PERSONA.md`「1日の使い方(夜)」が「必要であればターミナルに戻り`orgh report --days 1`を直接叩く。GUIとCLIを併用することに抵抗はない」と明記しており、対象ペルソナ自身がCLI代替を許容している。日常操作の直後の穴(P0群)ほどの緊急性は無い。
- **やること**:
